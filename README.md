# CRM Calls & Meetings API

REST API для учёта звонков организациям и назначения встреч менеджерам.
Тестовое задание «Software Developer» для ЧК «WhiteList & Co Ltd».

**Стек:** Java 21, Spring Boot 3.5 (Web, JDBC, Validation), SQLite (`sqlite-jdbc`, без ORM, запросы через `JdbcTemplate`), JUnit 5 + AssertJ, Maven.

## Запуск с нуля

Нужен только **JDK 21** (`java -version`), версия **21.0.3 или новее**. Устанавливать Maven не нужно: в репозитории есть Maven Wrapper (`mvnw`), он сам скачает Maven при первом запуске.

> Почему именно 21.0.3+: с 1 марта 2024 года Казахстан перешёл на единый пояс UTC+5. Более старые сборки JDK содержат устаревшую базу часовых поясов, в которой Asia/Almaty = UTC+6. С ними рабочие часы будут считаться неверно.

### Linux / macOS

```bash
git clone https://github.com/Kojizz/crm-meetings-api.git
cd crm-meetings-api
./mvnw spring-boot:run
```

### Windows (PowerShell или cmd)

```powershell
git clone https://github.com/Kojizz/crm-meetings-api.git
cd crm-meetings-api
.\mvnw.cmd spring-boot:run
```

После запуска:

- API: http://localhost:8080
- первый запуск дольше обычного: wrapper скачивает Maven и зависимости.

При старте приложение применяет `src/main/resources/db/schema.sql` и `data.sql` и создаёт файл БД `crm.db` в текущей папке. Скрипты идемпотентны (`CREATE TABLE IF NOT EXISTS`, `INSERT OR IGNORE`), поэтому повторный запуск данные не теряет.

### Docker (необязательно)

```bash
docker compose up --build
```

Сборка идёт внутри контейнера, JDK на машине не нужен. БД хранится в volume `crm-data`.

| Переменная      | По умолчанию | Назначение          |

## Тесты

```bash
./mvnw test          # Windows: .\mvnw.cmd test
```

Интеграционные тесты поднимают приложение на случайном порту с отдельной временной БД и ходят в него настоящими HTTP-запросами. Перед каждым тестом таблицы очищаются. Даты вычисляются относительно текущей даты (ближайший понедельник), поэтому тесты не устаревают.

| Класс | Что проверяет |
|---|---|
| `WorkingHoursTest` | **граница рабочего дня**: 09:00 и 17:00 разрешены; 08:59, 17:01, 17:30 и 18:00 запрещены; пятница 17:00 разрешена; суббота и воскресенье запрещены; часы проверяются по Алматы, а не по UTC; время без часового пояса, с секундами или в прошлом отклоняется |
| `MeetingApiTest` | **пересечение встреч**: 10:00–11:00 и 11:00–12:00 допустимы, 10:30 и 09:30 дают 409; правило «одна организация — не две встречи одновременно» для разных менеджеров; перенос сохраняет `original_start_at` и историю; неудачный перенос ничего не меняет; отмена освобождает слот; отменённую встречу нельзя изменить; **8 параллельных запросов на один слот дают ровно одну встречу** |
| `CallApiTest` | `meeting_set` без встречи, с несуществующей, чужой или отменённой встречей отклоняется; `meeting_id` при другом результате отклоняется; одну встречу нельзя привязать к двум звонкам; результат звонка меняет статус организации |
| `CompanyApiTest` | создание, дубль БИН (409), невалидный БИН (422 с полем), пагинация, неверные `status` и `limit`, битый JSON и лишнее поле (422, а не 500) |
| `ScheduleApiTest` | расписание за локальный день Алматы, без отменённых встреч и чужих менеджеров, с сортировкой; 404 и 422 |
| `TimePolicyTest` | unit-тесты перевода времени и правила рабочих часов без Spring |

## Примеры запросов

Файл [`requests.http`](requests.http) содержит 21 запрос: успешные сценарии и все виды отказов, с ожидаемым кодом в заголовке. Открывается в IntelliJ IDEA (встроенный HTTP Client) или в VS Code (расширение REST Client). Запросы выполняются по порядку на пустой БД.

Пример через curl:

```bash
curl -X POST http://localhost:8080/companies -H "Content-Type: application/json" \
  -d '{"name": "ТОО Алматы Трейд", "bin": "170340021554", "phone": "+7 701 111 22 33"}'

curl -X POST http://localhost:8080/meetings -H "Content-Type: application/json" \
  -d '{"company_id": 1, "manager_id": 1, "start_at": "2030-01-07T05:00:00Z"}'
```

## Эндпоинты

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/companies` | добавить организацию (`name`, `bin`, `phone`) |
| GET | `/companies?status=&limit=&offset=` | список с фильтром по статусу и пагинацией (`limit` 1–100, по умолчанию 20) |
| POST | `/calls` | результат звонка: `no_answer`, `refused`, `meeting_set` (+ `meeting_id`) |
| POST | `/meetings` | назначить встречу (`company_id`, `manager_id`, `start_at`) |
| GET | `/meetings/{id}` | встреча с историей изменений |
| PATCH | `/meetings/{id}` | перенести (`{"start_at": ...}`) или отменить (`{"status": "cancelled"}`) |
| GET | `/managers/{id}/schedule?date=YYYY-MM-DD` | расписание менеджера на день по Алматы |

JSON-поля пишутся в `snake_case`, неизвестные поля в запросе отклоняются.

### Формат ошибок

Все ошибки возвращаются в одном формате:

```json
{"error": {"code": "conflict", "message": "Manager 1 already has meeting 3 from 2030-01-07T05:00:00Z to 2030-01-07T06:00:00Z"}}
```

| Код | `error.code` | Когда |
|---|---|---|
| 404 | `not_found` | организация, менеджер или встреча не найдены |
| 409 | `conflict` | пересечение встреч, дубль БИН, изменение отменённой встречи, повторная привязка встречи к звонку |
| 422 | `validation_error` | неверный формат запроса (с полем `details`: какое поле и что не так) |
| 422 | `business_rule_violation` | нарушено бизнес-правило: рабочие часы, прошлое, звонок `meeting_set` без встречи |
| 404/405/415 | `http_error` | неизвестный путь, неподдерживаемый метод или Content-Type |
| 500 | `internal_error` | непредвиденная ошибка, без стектрейса наружу |

## Как реализованы бизнес-правила

1. **60 минут.** Клиент передаёт только `start_at`, а `end_at = start_at + 60 мин` считает сервер (`TimePolicy.MEETING_DURATION`).
2. **Рабочие часы.** `TimePolicy.workingHoursViolation` переводит время в `Asia/Almaty`. Встреча разрешена, если день пн–пт, начало ≥ 09:00 и конец ≤ 18:00 того же дня. Поэтому 17:00 разрешено, а 17:30 нет.
3. **Пересечения у менеджера.** Интервалы полуоткрытые `[start, end)`: конфликт есть, если `start < other_end AND end > other_start`. Встреча 11:00 сразу после 10:00–11:00 конфликтом не считается. Учитываются только активные (`scheduled`) встречи.
4. **Пересечения у организации.** Та же проверка, но по `company_id` и для любых менеджеров.
5. **`meeting_set`.** Сначала создаётся встреча (`POST /meetings`), затем звонок с `result=meeting_set` и её `meeting_id`. Встреча должна существовать, принадлежать той же организации и не быть отменённой.
6. **История переноса.** `original_start_at` никогда не меняется. Каждое действие (`created` / `rescheduled` / `cancelled`) пишется в таблицу `meeting_history` и возвращается в поле `history`.
7. **Ошибки.** Свои исключения (`NotFoundException` / `ConflictException` / `BusinessRuleException` / `ValidationException`) и `GlobalExceptionHandler` переводят ошибки в корректный HTTP-код. Обработчик `Exception` гарантирует, что даже неожиданная ошибка вернёт JSON, а не стектрейс.

**Время.** На вход принимается ISO 8601 с часовым поясом (`Z` или `+05:00`). Время без пояса отклоняется с 422, чтобы не угадывать, что имел в виду клиент. На выходе всегда UTC в формате `YYYY-MM-DDTHH:MM:SSZ`. В БД время хранится строкой фиксированного формата, поэтому сравнение строк в SQL совпадает со сравнением времени.

**Гонки.** Подключение к SQLite настроено с `transaction_mode=IMMEDIATE`, поэтому каждый `@Transactional`-метод начинается с `BEGIN IMMEDIATE` и сразу берёт блокировку записи. Проверка слота и вставка встречи выполняются в одной такой транзакции, так что два параллельных запроса на один слот идут строго по очереди, и второй получает 409. Подробнее в `REFLECTION.md`.

## Принятые решения по неоднозначностям

- **Менеджеры** создаются скриптом `data.sql` (id 1, 2, 3), потому что эндпоинта для них в ТЗ нет.
- **Статус организации** равен результату последнего звонка: `new` → `no_answer` / `refused` / `meeting_set`. По нему работает фильтр `GET /companies?status=`.
- **Правило 4** («не две активные встречи одновременно») понято как запрет пересечения по времени. Две встречи одной организации в разное время разрешены.
- **Встреча в прошлом** отклоняется (422) при создании и переносе.
- **`start_at` должен быть кратен минуте** (секунды = 00), иначе 422.
- **Перенос** меняет только время. Менеджер встречи не меняется. Перенос на то же время возвращает 422.
- **Несуществующая организация или менеджер в теле запроса** дают 404. Несуществующая встреча в звонке `meeting_set` даёт 422, потому что ТЗ называет это ошибкой валидации.
- **Отменённую встречу** нельзя ни перенести, ни отменить повторно (409).
- **Праздничные дни РК** не учитываются, только пн–пт.

## Что сделано и что нет

**Сделано:** все 6 эндпоинтов из ТЗ плюс `GET /meetings/{id}` для просмотра истории; все 7 бизнес-правил; SQL-схема; 44 теста (40 интеграционных и 4 unit); `requests.http`; Docker.

**Не сделано:**
- производственные календари и праздники РК;
- фильтрация списка организаций по чему-либо, кроме статуса;
- список звонков и встреч (`GET /calls`, `GET /meetings`): в ТЗ их нет;
- продакшн-БД (PostgreSQL) и версионные миграции (Flyway). Сейчас схема создаётся идемпотентным SQL-скриптом. Переход описан в `REFLECTION.md`.
